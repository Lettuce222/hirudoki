# ADR 0016: UX変更は画面遷移の本人承認後に実装する

- Status: Accepted
- Date: 2026-11-19
- Linear: LET-15 / LET-26 / LET-28

## Context

ユーザーは、ユーザー体験を変える全ての実装について、チケットに取り組む前に画面遷移図を作成し、本人のレビューが通ってから実装を開始するよう指定した。

## Decision

- 対象チケットごとにdocs/uxへ画面遷移図を置き、Linearからリンクする。複数チケットが同じフローを構成する場合は共通の図を参照できる。
- レビューは基本の正常系を1本通し、画面の順序、入力タイミング、完了後の到着点という体験の認識を合わせる。エラー・境界条件の網羅的なシミュレーターにはしない。細かな入力制約やエラー条件は本体実装時にTDDで詰める。
- 初期状態はレビュー待ちとし、本人による明示的な承認と図のrevisionを記録してから実装する。図の作成や時間経過だけでは承認扱いにしない。
- 本人が画面を操作しながら短い説明も読める、簡単なHTMLプロトタイプを主なレビュー資料とする。Markdownの図は補助資料に留め、HTMLの試作品作成と本体の実装を区別する。
- 承認後に遷移を変える必要が生じたら、その変更を図に反映して再承認を得てから実装する。
- 必要性や理由を尋ねる議論の質問を、案への反対・承認・変更指示として扱わない。説明と選択肢を提示し、明示的な指示・承認があってから方針を変える。
- UXを変えない静的検査、環境設定、調査などはこの画面レビューの対象にしない。

## Alternatives considered

- 実装後のPRレビューだけで確認する: 方針が違った場合の手戻りが大きく、本人の指定した順序を満たさない。
- 全ての技術作業まで画面承認待ちにする: 画面を持たない作業には適用せず、UX変更の境界に絞る。

## Consequences

AGENTS.mdの必須手順とする。この承認を得ても、TDD、異常系、モバイル、開発環境から本番の検証という完了条件は変わらない。最初の認証フロー案はdocs/ux/02-authentication-flow.mdに置き、レビュー待ちとする。

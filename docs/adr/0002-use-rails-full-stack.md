# ADR 0002: Railsフルスタックを採用する

- Status: Accepted
- Date: 2026-11-16

## Context

課題では、CRUD、認証、画像、複雑な業務ルール、管理機能、model spec、system specを30時間以内に実装する必要がある。フロントエンドを別アプリケーションにすると、API設計、認証連携、ビルド、デプロイ、E2Eテストの対象が増える。

## Decision

バックエンドとフロントエンドの両方にRuby on Railsを使用する。サーバーサイドレンダリングを基本とし、必要な操作性だけをRails標準のフロントエンド機構で補う。

データベースには、開発環境と本番環境の差を減らすためPostgreSQLを使用する。

## Alternatives Considered

### Rails API + SPA

フロントエンドの表現力は高いが、今回の要件に対して構成要素と障害点が増え、30時間の制約に合わないため不採用とした。

### Rails + SQLite

初期構築は容易だが、採用候補のPaaSでは永続化や複数プロセスとの相性に問題があり、本番との差も生じるため不採用とした。

## Consequences

### Positive

- 一つのアプリケーションで画面、業務ロジック、認証、テストを扱える。
- system specで利用者操作を端から端まで検証しやすい。
- デプロイ対象が一つになる。

### Negative

- クライアント側で複雑な状態管理が必要なUIには向かない。
- Railsの規約に沿って関心を分離しないと、モデルやコントローラーが肥大化しやすい。

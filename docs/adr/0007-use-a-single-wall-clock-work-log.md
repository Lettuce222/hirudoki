# ADR 0007: 作業時間を単一の壁時計で記録する

- Status: Accepted
- Date: 2026-11-16

## Context

技術試験では、課題に使った30時間の内訳を最終的に報告する必要がある。計画、意思決定、環境構築、アカウント準備、実装、テスト、デプロイ、提出準備を含む全作業を追跡しなければならない。一方、複数エージェントや複数作業が並行すると、それぞれの所要時間を合算する方式では実際の経過時間を二重計上する。

## Decision

- プロジェクト全体で同時に一つだけ進行できる、単一の壁時計セッションを使う。
- 正本は追記専用の `docs/work-log/work-log.jsonl` とし、提出確認用の `summary.md` をそこから生成する。
- 並列作業は別セッションにせず、進行中セッションのノートとして記録する。カテゴリをまたぐ場合は `mixed` にする。
- 順番に作業フェーズが変わる場合はセッションを分ける。
- 過去時間を復元するときは `estimated` を明示し、既存時間帯との重複を拒否する。
- `AGENTS.md` とプロジェクトローカルの `work-log` skillにより、課題関連作業の開始・中断・終了時の記録を必須にする。

## Alternatives considered

### 各エージェント・各タスクの時間を個別に記録して合算する

内訳は細かくなるが、並列作業を二重計上し、30時間という実時間制約を正しく表せないため採用しない。

### Linearの作業時間だけで管理する

進捗との紐付けには優れるが、ローカルでの環境構築や提出準備を漏れなく記録する用途と、監査可能な追記専用ログには向かない。Linear issue IDはログ側から関連付ける。

### 手書きのMarkdown表だけで管理する

手軽だが、重複・計算誤り・過去行の変更を機械的に防げないため採用しない。

## Consequences

- 実際の経過時間と提出合計が一致しやすくなる。
- JSONLからカテゴリ別・作業別の内訳を再生成できる。
- 並列作業のカテゴリ別分単位内訳は厳密には分離できないため、その場合は `mixed` とノートで説明する。
- 作業前後にログコマンドを実行する運用コストが生じる。

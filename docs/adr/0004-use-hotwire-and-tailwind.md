# ADR 0004: ERB、Hotwire、Tailwind CSSを採用する

- Status: Accepted
- Date: 2026-11-16

## Context

利用者向け画面と管理者向け画面を、PCとモバイルの両方で操作できる品質にする必要がある。制限時間は30時間であり、フロントエンドを別アプリケーションとして構築すると、状態管理、API、認証、ビルド、デプロイ、E2Eテストの対象が増える。

一方で、注文フォーム、絞り込み、確認操作、エラー表示などには、サーバーサイドレンダリングを基本としながら必要な箇所だけ対話性を追加できれば十分である。

## Decision

フロントエンドには次の構成を採用する。

- HTMLテンプレート: ERB
- 画面遷移と部分更新: Turbo
- クライアント側の小さな振る舞い: 必要最小限のStimulus
- CSS: Tailwind CSS

JavaScriptで業務状態を二重管理しない。業務ルールと最終的な入力検証はRails側に置く。

## Alternatives Considered

### React、VueなどによるSPA

複雑なクライアント状態には適するが、API境界、認証連携、フロントエンドビルド、E2Eテストが増え、今回の制限時間には見合わないため不採用とした。

### ERBと素のJavaScript

依存は少ないが、部分更新やフォーム操作を個別に実装するとコードが散らばりやすいため不採用とした。

### Bootstrap

既成コンポーネントで短時間に画面を構築できる。一方で、今回の画面構成に合わせたデザイン調整と一貫したレスポンシブ設計をユーティリティクラスで行いやすいことからTailwind CSSを選択した。

## Consequences

### Positive

- Rails内で画面、認証、バリデーション、system specを一貫して扱える。
- SPA用のAPIとクライアント状態管理が不要になる。
- Tailwind CSSにより、レスポンシブ対応とデザイン規則を同じマークアップ上で表現できる。
- JavaScriptを必要な箇所へ限定できる。

### Negative

- Turboのフレーム・ストリーム更新では、通常のHTML遷移とは異なる挙動を理解する必要がある。
- Tailwind CSSのクラスがビューに集中すると可読性が下がるため、共通パーツをpartialやヘルパーへ抽出する必要がある。
- 高度なクライアント側状態管理が必要になった場合は適さない。

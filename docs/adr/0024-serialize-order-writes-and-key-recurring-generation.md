# ADR 0024 競合制御はDB制約・条件付き更新・固定順の行ロックを使い分ける

- Status: Accepted
- Date: 2026-11-26
- Linear: [LET-19](https://linear.app/lettuce222/issue/LET-19)・LET-34・LET-36・LET-37・LET-39・LET-40・LET-41

## 方針

1. 一意性はDBの一意制約で保証する。保存時の競合は、該当する制約の違反を識別して業務上の結果に変換する。
2. 現在の値と許可条件が1行に収まる更新は、条件を `WHERE` に含める。更新件数で成功を判断する。
3. 複数行の集計を守る書き込みは、共通の親行を固定順でロックする。ロック取得後の集計と保存を同じトランザクションで行う。

## 注文と評価への適用

- 注文の書き込みでは、利用者 → 日別献立 → 対象注文（既存注文の操作時）の順で共通の行をロックする。利用者行は献立をまたぐ同日3個の上限を、日別献立行は手動注文の提供数上限を守る。定期生成も同日上限を確認し、残数の確認は省く。
- 新規注文では弁当と配達エリアの `FOR SHARE` を維持する。販売停止やエリア無効化が先に確定した場合は、最新の状態を読んで注文を拒否する。注文が先に確定した場合は、確定時の単価と受付条件で受け付けた注文として扱う。
- 評価は投稿時にDBで受取済みか確認する。注文行の明示的なロックは省き、確認から保存までの間に状態が変わる競合は許容する。評価の `order_id` に一意制約を設け、同時投稿で競合した側は「評価済み」とする。
- 定期注文の生成は、生成元設定と提供日の組に一意制約を設けて二重生成を防ぐ。キャンセル済みも制約の対象に含める。

## 定期注文の実装

PR #30 では、生成元設定と生成対象日を注文に保存する。設定の弁当タイプが後から変わって候補の献立IDが変わっても、生成元設定と提供日は変わらない。生成対象日は複合外部キーで参照先の献立の提供日と一致させる。生成済みの注文を別の日へ移さないよう、参照されている献立の日付編集を制約で防ぐ。手動注文の生成元設定と対象日は空欄にする。

## 検証

別々のDB接続から書き込みを重ねて、提供数上限、利用者の同日上限、評価と定期注文の二重作成を防ぐことを確認する。

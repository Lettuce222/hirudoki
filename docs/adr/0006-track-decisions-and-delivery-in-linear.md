# ADR 0006: 意思決定待ちと実装進捗をLinearで管理する

- Status: Accepted
- Date: 2026-11-16

## Context

30時間の中で、技術的な意思決定、アカウント準備、本番デプロイ、機能実装、品質保証、提出準備を並行して扱う必要がある。未決定事項と実装タスクが会話や文書に分散すると、依存関係や残り時間を見失いやすい。

一方、技術的な判断理由と代替案はリポジトリと一緒に提出・説明できる必要がある。

## Decision

進捗、担当状態、依存関係、見積時間、実績時間はLinearで管理する。技術的な意思決定の正式な記録は `docs/adr/` に置き、Linearの意思決定タスクから該当ADRへリンクする。

Linearでは一つのプロジェクトを作成し、次のインクリメントで整理する。

1. 準備・設計
2. Walking Skeleton
3. 認証・権限
4. 献立閲覧
5. 手動注文
6. 注文後操作
7. 定期注文
8. 管理業務
9. 完全性・提出確認

課題には次の分類を付ける。

- `decision`: 合意とADR化が必要な意思決定
- `setup`: アカウント、環境、CI、デプロイ準備
- `feature-slice`: 利用者または管理者へ価値を届ける縦方向のスライス
- `submission`: シード、README、作業ログ、提出確認

テスト、認可、堅牢性、UI/UX、モバイル、本番確認を独立した後工程の課題にはしない。各 `feature-slice` の完了条件に含める。横断的な基盤変更だけは独立課題として扱う。

各課題には少なくとも次を記載する。

- 目的と受入条件
- 前提となる課題または意思決定
- 時間予算
- 実績時間
- TDDのTODOまたは対象となる振る舞い
- 開発環境と本番環境での確認項目
- 関連ADR

## Alternatives Considered

### Markdownだけで管理する

リポジトリと一緒に残せるが、状態変更、依存関係、一覧性、残時間の把握が弱いため、進捗管理の主手段にはしない。

### GitHub Issuesだけで管理する

コードとの連携は強いが、今回ユーザーが望むLinearでの計画・進捗管理に比べ、意思決定待ちとインクリメントの俯瞰に使わないこととした。

## Consequences

### Positive

- 未決定事項と残タスクを同じ一覧で確認できる。
- 依存関係と時間予算を見ながら着手順を調整できる。
- Linearは進捗、ADRは判断根拠という責務を分離できる。

### Negative

- LinearとリポジトリのADR間でリンクと状態を同期する必要がある。
- Linearへアクセスできない状況でも判断根拠が失われないよう、ADRを正本として維持する必要がある。
